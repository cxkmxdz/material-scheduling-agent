# 素材审核与发布排期 Agent 实施复盘

本次已交付可运行的离线链路、真实 API 决策循环实现和本地验证证据；真实模型验收仍因缺少配置未完成。这是本次实施过程记录，不是候选人的经历或学习自述。

## 证据和决策的边界

实际实现中最需要保护的是“模型说保存成功”与“数据库确有记录”的区别。最终设计不接受模型传回成功状态和草稿 ID，finish 只结束决策，运行器最后读取 SQLite。工具校验素材、规则和可用时段证据，并在事务中复查冲突。相关测试还验证了模型直接 finish、伪造审核字段和使用 confirmed 参数都不能越过边界。

另一个具体取舍是硬性时刻冲突后的建议。若将 19:00 建议直接算作已确认，模型就替用户改变了要求。因此确认状态由工具根据原请求自动推导，模型没有确认权限；建议可持久化供评审，但不占位。未来如果增加确认动作，需要重新检查冲突，不能直接提升旧建议。

## 测试如何推动修改

第一批 49 项测试中，有 14 项失败，原因是 INSERT 占位符数量不一致。此前保存工具将 SQLite 异常安全转换为失败，因而未虚报成功；但正常业务同样无法保存。并发和保存测试暴露了具体错误，修复为显式列名后全部通过。这说明仅检查“有失败处理代码”不足以证明正常持久化能用，必须核对真实数据库。

后续检查发现，JSON null 函数参数需要在访问字典前明确拒绝；字符串级日志替换不能稳妥覆盖带引号或换行的密钥，于是改为递归替换再序列化。测试同时确认 Trace 不被覆盖、异常响应体不进入日志，保存故障是在真实 INSERT 后触发回滚。

## 可复现和诚实报告

Mock 适合在无凭据环境验证业务链路，HTTP 假响应适合验证协议，但两者都不能证明真实模型会根据占用或保存错误做出合理动作。为补齐这个缺口，实现了同请求、同模型、仅改变工具条件的真实对照脚本。当前只记录配置缺失，不生成假真实 Trace，也不宣称 A11 已通过。

示例由运行脚本生成，附数据库导出及 SHA256 清单；测试报告记录实际版本、数量和耗时。依赖锁、输出独占创建和新数据库路径让评审能重复运行并保留旧证据。

## 后续工作和用时

优先下一步是配置真实模型并完成三组对照，依据实际 Trace 修正提示或兼容问题；随后由候选人审阅 AI 记录、补充真实人工贡献并准备评审可访问的 GitHub 仓库。其他改进可包括带权限和再次冲突检查的人工确认入口、更完整的素材字段与真实规则、按业务需求设计的草稿过期和占位释放。这些均尚未实现。

本次可测量阶段的起止和耗时写入 `examples/execution-metadata.json`，范围为新项目目录创建至本地交付校验，不包含此前计划制作，也不代表候选人总用时。计划中的约三小时属于估计，不当作实际投入。
